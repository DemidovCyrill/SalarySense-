# Соответствие и зарплаты
Статус: PROPOSED, scoring_version=matching-v0.1. До продуктового ревью не выдавать формулу за подтверждённую пользователем.

## Принципы
Один набор требований и знаменатель для заявленного и проверенного покрытия. Неизвестное даёт нулевой вклад в подтверждённое покрытие, но отображается как unknown, а не как отсутствие способности. Это нижняя доля подтверждённых требований, не оценка всей компетентности и не вероятность найма.
Явно отделять required skill, optional skill и hard constraint. Похожесть embedding используется для поиска терминов, не для процента соответствия.

## Атомарное требование
Каждое требование имеет skill_id, scope_id, expected_credit r в (0,1], weight w>0 и mandatory. Доказательства применяются только к совместимому scope; квиз по базовым локаторам не закрывает архитектуру UI-фреймворка.
self_credit s и verified_credit v в [0,1]. Самооценку можно предложить по лестнице 0.25/0.5/0.75/1, но это условная продуктовая шкала, не эмпирически доказанная равноинтервальность. Результат квиза не переносится напрямую на практический scope.
Для каждого требования: p=min(1,max(s,v)/r); c=min(1,v/r). Таким образом проверенное включается в общий профиль, C ≤ P.
P=100×Σ(w×p)/Σw; C=100×Σ(w×c)/Σw. Округление один раз для отображения до целого, расчёт без промежуточного округления. Неизвестные навыки и непроверенные scopes показываются отдельным списком.
При Σw=0: scores=null, status=insufficient_data. Не заполнять отсутствующие веса эвристикой модели в runtime.

## Числовой пример
Четыре требования с r=1, весами 3,3,2,2. Пары (s,v): Java (1,1), API (0.75,0.5), SQL (0.5,0), CI (0,0).
Общий профиль: (3 + 2.25 + 1 + 0)/10 ×100 = 62.5 → 63%.
Подтверждено: (3 + 1.5 + 0 + 0)/10 ×100 = 45%.
SQL заявлен и не проверен; CI неизвестен. Нет вывода, что CI не умеет. Пример JSON в examples/match_calculation.json; независимый проверочный расчёт в tools/verify_package.py.

## Обязательные условия
Язык, локация, формат, необходимые разрешения: pass/fail/unknown. Не увеличивают и не уменьшают скрыто skill score. Вакансия с fail остаётся доступной, но не попадает в «без известных препятствий». Mandatory skill с нулевым вкладом отмечается даже при высоком общем score.
Сортировка: сначала соответствие пользовательским hard filters; затем P или C по явному выбору; unknown не скрывать; стабильный tie-break по job_id. Не считать пробел критичным только потому, что LLM так решила.

## Уровни
GradeProfile содержит критерии роли и обязательные dimensions. MVP показывает покрытие каждой модели, а не присваивает официальный титул. Утверждённого общего порога «80%=Middle» нет. При отсутствии reviewed-профиля — insufficient_data. Senior и Lead требуют наблюдений по практике/самостоятельности/ответственности; только quiz даёт preliminary/knowledge_only. Expert источника не переименовывается в Lead.

## Зарплатная выборка — salary-v0.1
Фильтры: роль, регион, формат, дата snapshot, валюта, tax_mode, период оплаты, активность и одинаковый data_mode. Считать уникальные вакансии, а не карточки-дубли.
Основная метрика: медиана midpoint=(min+max)/2 для двусторонних месячных вилок одной валюты и налогового режима. Явно писать «медиана середины опубликованных вилок», не «средняя зарплата специалистов». Квартили рассчитывать линейной интерполяцией позиции (N−1)×q.
Односторонние вилки не терять: отдельно число «от», «до»; в midpoint-медиану не включать. Null/ноль/ошибка парсинга исключаются с причиной. Gross/net/unknown не смешивать; hourly/yearly без проверенного перевода не конвертировать.
При N<10 (предлагаемый порог) — «недостаточно данных» для агрегата и доступные отдельные предложения. Показывать N total, N with_salary, N eligible, период, excluded counts. Выбросы не удалять без объявленного правила. Курсы валют в MVP не нужны: фильтр по валюте.
Это предложения ограниченной выборки, не обещание дохода. Прогноз персональной зарплаты и ROI обучения вне MVP.
