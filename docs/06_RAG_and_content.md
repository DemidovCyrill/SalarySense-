# RAG и подготовка базы компетенций
## Назначение
RAG объясняет соответствие профиля критериям роли, ограничения проверки и причины расхождения с требованиями вакансии. Не рассчитывает зарплату или итоговый процент. Вакансии получаются через адаптер; отдельная векторная база вакансий не обязательна.

## Что входит в корпус
Карточка: role_id, skill_id, scope_id, dimension, уровень модели, наблюдаемые признаки, допустимое доказательство, ограничения, source_refs, version, review_status, usage_status.
Контент для retrieval создаётся из одной версии канонических записей, которую использует каталог. В корпус не входят private bank keys, ответы других пользователей, draft-критерии и неоплаченный/неразрешённый контент.

## Pipeline
1. Register: source manifest, права, версия/commit, язык, дата.
2. Extract: исходные файлы в staging; хеши; раздел и локатор сохраняются.
3. Normalize: стабильные ID, типы, aliases, role mapping; не объединять разные технологии по одному похожему слову.
4. Curate: перевести/адаптировать, отделить цитату от собственной рубрики, отметить конфликт источников.
5. Review: техническая проверка, проверка лицензии, второго участника; решение по публикации.
6. Index: одна смысловая карточка/рубрика на фрагмент; название роли, scope и ограничения остаются с критерием. Длинная карточка делится по границам критерия с parent_id.
7. Evaluate: контрольные запросы по ролям, негативные случаи, конфликты и отсутствующий контент.
8. Publish: атомарная версия corpus; возможность rollback.

## Retrieval — PROPOSED
Жёсткие фильтры published/allowed/corpus_version, роль и scope; затем keyword + vector поиск, объединение результатов и при необходимости rerank. Стартовый candidate k=20, генерации передавать не более 6 карточек; значения меняются по eval. Порог не переносится между embedding-моделями. Общие компетенции могут быть global и доступны нескольким ролям по явной связи.
Если не хватает совпадений, расширять до общего критерия навыка с пометкой ограничения. Не использовать чужую роль как молчаливую замену.

## Контракт генерации
Вход: match_result, разрешённые факты, выбранные criterion/source refs, язык. Выход: status, summary, claims[{text,criterion_ids,source_ids,evidence_ids}], missing_data, limitations. Числа копируются из Match, ссылки только из allowlist.
Проверки: все ID существуют и принадлежат контексту; выводы не шире scope; модель не добавляет новые зарплаты, грейды и опыт. Наличие ссылки само по себе не доказывает поддержку вывода — на пилоте нужна ручная выборочная проверка смысловой поддержки.

## Отказы
no_context → insufficient_data; провайдер недоступен → partial с числовым результатом; несовместимая роль → отказ; конфликт источников → явное описание разницы. Один retry только для временного сбоя; не бесконечные вызовы модели.

## Создание банка вопросов
Критерий → черновик вопроса → обоснование ответа → правдоподобные дистракторы → ручная проверка → publish version. Нельзя считать генерацию ИИ валидацией. Ключи хранятся только на сервере, объяснение показывается после завершения. Фиксированный банк предпочтительнее случайной генерации на каждый запрос.
3–5 вопросов дают первичный сигнал. Показывать scope и количество вопросов. Для senior/lead знания не заменяют практику и ответственность. Не заявлять психометрическую точность без исследования.

## Eval и release gate — PROPOSED
Сбалансировать роли и негативные кейсы; отдельный dev/test split, не включать test в few-shot. Для старта: 60 вопросов, минимум 2 на семейство ролей плюс неизвестные случаи. Recall@5 ожидаемых критериев ≥0.85; доля смыслово поддержанных проверенных claims ≥0.95; 100% синтаксически существующих citations; 0 раскрытий answer keys и чужих профилей на safety suite. Значения — цели команды, не измеренные результаты; report содержит модель, corpus, prompt hash, дату, стоимость и N.
