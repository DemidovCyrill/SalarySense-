# План реализации и backlog
Оценки предварительные; участники и доступность команды неизвестны. Каждой задаче назначается владелец на старте спринта. Охват всех IT не сокращается до QA: объём контента и степень проверки каждой роли контролируются отдельно.

| Этап | Результат | Зависимость | Предлагаемый срок |
|---|---|---|---|
| M0 | Review документации, каталог ролей, провайдеры, назначения | Нет | Неделя 1 |
| M1 | Версионированный каталог, профиль, UI-навигация | M0 | Недели 1–2 |
| M2 | Банк вопросов, короткие проверки и evidence | M1 | Недели 2–3 |
| M3 | Snapshot вакансий, скоринг и рыночные агрегаты | M1, правила данных | Недели 3–4 |
| M4 | RAG-объяснение с источниками и отказами | M2,M3, reviewed criteria | Недели 4–5 |
| M5 | Письмо, UX состояний, безопасность, eval | M4 | Недели 5–6 |
| M6 | Пилот, исправления, приватная демонстрация | M5 | Недели 7–8 |

Четырёхнедельный вариант: один demo snapshot с несколькими записями по каждой группе ролей; покрытие отображается честно; письмо можно упростить до шаблона по фактам. Нельзя экономить время скрытой генерацией «подтверждённых» критериев.

## Критический путь
Role taxonomy → reviewed source/criteria → evidence scope → scoring → explanation → eval. UI можно разрабатывать на fixtures по контракту. Live API не блокирует demo при сохранении mode.

## Владельцы функций
Product owner: решения об охвате/приёмке; Content reviewer: качество критериев/вопросов; Frontend: интерфейс и доступность; Backend: данные/скоринг/API; QA: проверки и фиксация ограничений; Operator: секреты и приватная среда. Люди и состав команды OPEN, фамилии не выдуманы.

## Приоритеты
P0: specs/001–006, приватность, контроль demo, отказ без контекста. P1: specs/007 письмо, закладки. P2: трекер откликов, регулярные уведомления, обучение, импорт резюме — отдельные будущие изменения, не скрытые требования текущего выпуска.
