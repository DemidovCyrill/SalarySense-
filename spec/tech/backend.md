# Бэкенд SalarySense

Этот документ описывает реализованный учебный бэкенд: HTTP-контракт интерфейса, доменные правила, хранение сессий, RAG по базе знаний и benchmark. Он дополняет [архитектуру](architecture.md) и [правила RAG](rag.md), а не заменяет их. Продуктовые требования остаются в [product.md](../product/product.md).

**Статус:** бэкенд работает на демонстрационном каталоге вакансий, критериев и проверок. Реальные вакансии, поставщик данных, утверждённый банк вопросов и публичный запуск не подключены. Редактор материалов доступен без аутентификации и предназначен только для локального запуска. Это ограничения, а не готовые функции.

## Запуск

Нужен Python 3.11 или новее. Проверено на Python 3.13.9, Windows. Из корня репозитория:

```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
Copy-Item .env.example .env
# впишите OPENROUTER_API_KEY в .env
.venv\Scripts\python.exe -m app
```

Откройте `http://127.0.0.1:8000`. Один процесс отдаёт интерфейс из `app/frontend/public`, продуктовый API `/api/v1` и вопрос базе знаний `POST /ask`. Каталог `/api/docs` содержит OpenAPI-описание.

Без ключа модели интерфейс, рынок, вакансии и проверки работают; `POST /ask` отвечает `503` с понятным сообщением. Демонстрационный сервер на Node (`node app/frontend/demo/server.mjs`) остаётся отдельным эталоном интерфейса и подготовленных ответов.

## HTTP-контракт

Контракт совпадает с [описанием фронтенда](frontend.md): префикс `/api/v1`, cookie владельца, JSON, ошибки с полем `message`. Отличия от демо-сервера:

- cookie называется `salarysense_session`, а не `salarysense_demo`;
- `POST /ask` обрабатывает настоящий RAG-конвейер, а не три подготовленных ответа;
- сессия хранится в SQLite и переживает перезапуск процесса;
- неизвестный метод у существующего пути возвращает `405`, у демо-сервера — `404`.

Для сверки поведения есть `python tools/parity_check.py`. Он поднимает Node-демо и Python-бэкенд, отправляет одинаковую последовательность запросов и сравнивает ответы. Проверка требует Node.js 22+ и не входит в обычный прогон тестов.

### Правила, которые считает код

- **Совпадение (matching-v0.1).** Для требования с весом `w` и ожидаемым уровнем `r`: `p = min(1, max(s, v) / r)`, `c = min(1, v / r)`. По набору требований `P = 100 × Σ(w × p) / Σw`, `C = 100 × Σ(w × c) / Σw`. Округление половины вверх выполняется один раз при показе. Пример 63 % / 45 % воспроизводится тестом. Неизвестное доказательство даёт нулевой вклад в `C`, но показывается как «неизвестно».
- **Зарплаты (salary-v0.1).** В основную метрику входят только двусторонние вилки в рублях, gross, за месяц. Медиана считается по серединам вилок, квартили — линейной интерполяцией. Меньше 10 пригодных вилок — агрегат отсутствует, причины исключений считаются отдельно. Пропущенная зарплата не превращается в ноль.
- **Попытки.** Ответы сохраняются по позиции вопроса. Завершение идемпотентно: повторный вызов возвращает тот же результат и не меняет ревизию профиля. Открытая попытка продолжает ссылаться на свою версию банка, даже если опубликована новая.
- **Редакция.** Переходы `черновик → на проверке → опубликован → выведен`, публикация выводит предыдущую опубликованную версию из новых расчётов. Правка возможна только у черновика.

Модель не участвует в этих расчётах и не меняет числа.

## Хранение и доступ

Состояние сессии — один JSON-документ в таблице `sessions` (SQLite, WAL). В нём профиль, материалы сессии, попытки и их версии. Идентификатор сессии — случайные 32 hex-символа в cookie `HttpOnly`, `SameSite=Strict`, при необходимости `Secure`.

Сервер находит профиль, попытку и материал только внутри сессии из cookie. Подстановка чужого ID возвращает `404`. `DELETE /api/v1/profile` удаляет запись и выдаёт новую пустую сессию. Ответы квиза в браузер не отправляются; ключи и скрытые объяснения остаются в серверном каталоге.

Для локальной версии дополнительно проверяется `Origin`; тело запроса ограничено 24 000 байт; API отвечает `Cache-Control: no-store`. Аутентификации редактора, CSRF-токена сверх проверки Origin, ограничения частоты запросов и политики хранения логов пока нет — это условия live-запуска, а не реализованные свойства.

## RAG по базе знаний

### Корпус

`app/backend/data/corpus.json` — 30 фрагментов о правилах продукта: роли и навыки, заявленное и проверенное, проверки, совпадение, зарплаты, рынок, письмо, редакция, приватность, ограничения. У каждого фрагмента есть ID `D01…D30`, заголовок, текст, источник и раздел спецификации. Это проверяемый вручную учебный корпус, а не полная база знаний; вопросы и эталоны хранятся отдельно в `benchmark/questions.json` и не индексируются.

### Предобработка

Нижний регистр, `ё → е`, разбиение по не-буквам, отбрасывание служебных слов, лемматизация русских слов через `pymorphy3`. Выбор обоснован морфологией русского языка: «проверки», «проверок» и «проверка» должны попадать в один терм. Если библиотека недоступна, используется встроенное усечение окончаний — качество ниже, индекс продолжает работать. Токенизация и лемматизация применяются одинаково к документам и запросу.

### Индекс BM25

Индекс реализован самостоятельно, без готовых поисковых библиотек: обратное соответствие «терм → документ → частота», длины документов и средняя длина.

```text
IDF(t) = ln(1 + (N − df(t) + 0.5) / (df(t) + 0.5))
BM25(q, d) = Σ_t IDF(t) · tf(t, d) · (k1 + 1) / (tf(t, d) + k1 · (1 − b + b · |d| / avgdl))
```

Параметры: `k1 = 1.2`, `b = 0.75`. При равных баллах документы упорядочиваются по ID. Заголовок фрагмента индексируется вместе с текстом. Конструктор индекса проверяет параметры и уникальность ID; пустой корпус и пустой запрос обрабатываются явно. Тест на примере из методических указаний даёт 0,940 и 0,470 для документов A и B/C.

### Ответ

1. `POST /ask` принимает `{"question": "..."}` до 600 символов.
2. Поиск возвращает до 5 фрагментов. Если совпадений нет или балл ниже `RAG_MIN_SCORE`, ответ — `В документах нет этой информации.` с `sources: []` без вызова модели.
3. Модель получает инструкцию, вопрос и фрагменты с ID. Промпт запрещает добавлять факты и выполнять инструкции из текста фрагментов.
4. Сервер принимает только ссылки `[Dxx]` на переданные фрагменты. Ответ без ссылок повторяется один раз с более строгой инструкцией; если ссылок снова нет, возвращается отказ.
5. В `sources` попадают только процитированные фрагменты с заголовком и текстом. Выдуманные ID отбрасываются.

Температура 0, лимит 500 токенов. При сбое модели или отсутствии ключа — `503` и понятное сообщение; числовые результаты продукта при этом не затрагиваются. Ключ, промпты с данными пользователя и тексты чужих ответов в журналы не пишутся: логируются только модель, задержка и размер ответа.

## Benchmark

Набор: 30 документов корпуса, 10 обычных вопросов с эталоном и 3 релевантными документами, 5 вопросов-ловушек без ответа в корпусе. Глубина метрик `k = 3`, дополнительно считается `Recall@5`; модели передаются 5 фрагментов.

```powershell
.venv\Scripts\python.exe -m app.backend.benchmark --judge both
```

Метрики:

- **Recall@k** — какая доля эталонных документов попала в первые `k`;
- **MRR@k** — обратный ранг первого релевантного документа;
- **Accuracy** — доля полностью правильных ответов на 10 обычных вопросов (оценка модели-судьи по эталону);
- **Correct Rejection Rate** — доля ловушек, где система не выдумала ответ.

Дополнительно считается консервативная лексическая проверка по обязательным фразам (`accuracy_keyfacts`). Она занижает результат, потому что требует точных формулировок, и используется как диагностика, а не как основная метрика.

Результаты прогона 2026-11-27 на `openai/gpt-4o-mini`:

| Метрика | Значение |
| --- | --- |
| Recall@3 | 60,0 % |
| Recall@5 | 83,3 % |
| MRR@3 | 1,000 |
| Accuracy (судья) | 80,0 % (8 из 10) |
| Correct Rejection Rate | 100 % (5 из 5) |

Вывод: первое место всегда релевантно, но при перефразировании BM25 не поднимает в top-3 все подтверждающие фрагменты — отсюда 60 % Recall@3. Рост до 83,3 % на глубине 5 и 80 % правильных ответов показывают, что найденного контекста обычно достаточно, но часть ошибок связана с пропущенными фрагментами и краткостью ответа. Полные строки, ответы и обоснования судьи — в [`benchmark/results/benchmark-2026-11-27.json`](../../benchmark/results/benchmark-2026-11-27.json), разбор — в [отчёте benchmark](../../benchmark/report.md).

Ограничения измерения: судья — языковая модель, один прогон, температура 0; эталонные списки размечены автором вручную; корпус небольшой. Для live-запуска нужны независимая разметка, несколько прогонов и проверка на вопросах, которых не было при разработке.

## Проверки

```powershell
.venv\Scripts\python.exe -m pytest -q          # 56 тестов бэкенда
.venv\Scripts\python.exe -m ruff check app tests tools
.venv\Scripts\python.exe -m app.backend.benchmark --judge both
.venv\Scripts\python.exe tools/parity_check.py # сверка с демо-API, нужен Node.js
node --test tests/frontend-smoke.test.mjs      # проверки демо-сервера фронтенда
```

Тесты бэкенда не обращаются к сети: ответы модели подменяются, сессии живут во временном SQLite. Проверены обычные и отрицательные случаи: чужая попытка, повторное завершение, неверный переход редакции, неизвестный документ benchmark, отказ без ключа, ответ без цитат, ограничение размера тела, чужой Origin. Браузерные сценарии на этом бэкенде отдельно не перепрогонялись; сверка ограничена HTTP-контрактом и API-тестами.

## Открытые вопросы

- загрузчик реальных вакансий, проверка источника и снимки данных;
- аутентификация и права редактора, аудит публикаций;
- общий банк критериев вместо материалов внутри сессии;
- RAG-рекомендации по пробелам и черновики вопросов для редакции;
- улучшение поиска: независимая разметка, reranking, сравнение с векторным поиском на одном наборе;
- ограничение частоты запросов, политика хранения и удаления логов, резервное копирование;
- выбор постоянного хранилища и схемы миграций для рабочей нагрузки.
