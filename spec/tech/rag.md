# База компетенций, RAG и короткие проверки

Этот документ описывает будущую работу с критериями и вопросами для FR05–FR06 и FR12–FR14. RAG здесь означает: найти подходящие **проверенные фрагменты базы знаний** и дать модели только их для объяснения конкретного результата. Получение вакансий через API или парсер само по себе не является RAG. Зарплаты и проценты совпадения считает код по правилам из [архитектуры](architecture.md).

## Что входит в базу

Приложению нужен каталог для всех направлений IT, но не следует обещать одинаковую глубину оценки каждой роли в первый день. Для каждой роли отдельно показывают: есть ли список навыков, опубликованные критерии уровней и проверенные вопросы. Общий каталог можно пополнять постепенно. QA — пример, не единственная профессия.

Запись критерия отвечает на вопросы: к какой роли и теме он относится; какой наблюдаемый признак описывает; для какого уровня или вида ответственности нужен; чем это можно проверить; на каком источнике основан; что из этого **нельзя** заключить. Например, правильный ответ про SQL JOIN показывает знание этой темы, но сам по себе не подтверждает рабочий опыт с базами данных.

Для разработчика у записи должны быть устойчивые ID роли, навыка, темы и критерия, версия, источник, статус ревью и разрешение на использование. Источник хранит адрес или иной указатель на конкретный фрагмент, автора, дату/версию и права. Эти данные позволяют человеку открыть основание вывода и позволяют воспроизвести результат спустя время.

**Возможные источники, а не готовый корпус:** ESCO и O*NET для профессий и навыков; опубликованные матрицы компаний для примеров критериев; официальная документация инструментов для технических фактов. Корпоративная матрица не становится общей шкалой всего рынка. Материалы с отдельной лицензией, например SFIA, не импортируются без разрешения. В репозитории нет скачанных полных баз или проверенного банка вопросов. Права и точную версию каждого файла надо проверять перед использованием.

## Как материал становится доступным пользователю

1. Редактор регистрирует источник и право его использовать.
2. Материал поступает во временную область; сохраняются версия, исходный фрагмент и контрольная сумма.
3. Редактор связывает термин с нужной ролью, навыком и темой. Похожие слова не считаются одинаковыми навыками автоматически.
4. Он формулирует понятный критерий, отмечает собственную формулировку и пределы вывода.
5. Другой участник проверяет содержание и права, затем материал публикуется как новая версия.
6. Только опубликованные и разрешённые записи попадают в индекс для новых ответов. Старые результаты продолжают ссылаться на прежние версии.

Состояния материала: «черновик», «на проверке», «опубликован», «выведен из новых расчётов». Публикация не переписывает старую карточку. Удаление ошибочной версии из новых ответов не уничтожает сведения о том, по каким правилам был сделан старый вывод, если правила хранения допускают аудит.

## Как получается объяснение

Сначала сервер уже знает результат сравнения профиля с вакансией. Он ищет критерии **той же роли и той же темы** среди опубликованных и разрешённых записей. Для поиска можно начать с поиска по словам; добавление векторного поиска — техническое предложение, которое нужно сравнить с простым вариантом на одинаковых вопросах. Чужая роль не подставляется в ответ только потому, что её текст похож.

Модель получает минимум данных: рассчитанные числа, разрешённые факты данного пользователя, выбранные критерии и исходные фрагменты вакансии. Она формулирует объяснение простым языком. Сервер принимает ответ только если каждое важное утверждение ссылается на переданные критерии, источники и доказательства и не выходит за пределы проверенной темы. Ссылки, новые суммы зарплат, уровни и достижения нельзя выдумывать.

Если подходящего критерия нет, ответ — «недостаточно данных». Если модель недоступна, сайт сохраняет числовое сравнение и исходные требования, а словесный разбор помечает недоступным. Если источники спорят друг с другом, расхождение показывается; модель не выбирает правило молча. Инструкции, встречающиеся в тексте вакансии, остаются текстом вакансии и не меняют правила приложения.

## Как готовятся короткие тесты

По опубликованному критерию редактор готовит вопрос, варианты ответа, правильный ответ и объяснение. ИИ может помочь с черновиком, но это не проверка его качества. Другой участник проверяет точность, неоднозначности и правдоподобность вариантов. Банк публикуется с версией; начатая попытка использует одну зафиксированную версию до завершения.

Человеку перед тестом показывают тему, примерное время, число вопросов и пределы вывода. Несколько вопросов, в том числе ответ «не знаю», позволяют дать первичный сигнал о конкретных знаниях. Они не подтверждают весь навык, рабочий стаж, самостоятельное проектирование или руководство командой. Для senior и lead нужны другие свидетельства практики и ответственности; их подготовка требует отдельной рубрики и ревью.

Ключи ответов и скрытые объяснения остаются на сервере. Публичная версия вопроса не содержит их. Завершённая попытка создаёт одно доказательство с датой, темой и версией; повторное завершение не создаёт второе.

## Как проверять качество перед запуском

Команда собирает примеры для разных направлений IT и отдельно отрицательные случаи: нет критерия, похожий навык из другой роли, противоречивые источники, инструкция внутри вакансии, попытка получить ключ ответа или чужие данные. На одном наборе вопросов сравниваются ответ без RAG, простой поиск и выбранный вариант RAG. Проверяют, найден ли нужный критерий, действительно ли источник поддерживает каждое утверждение, верно ли система отказывает при нехватке данных и сколько стоит вызов модели.

Результат проверки записывается вместе с версией корпуса, модели и промпта, датой, размером выборки и ошибками. Порог качества и выборка должны быть согласованы до включения live-функции. В этом репозитории benchmark и реальные проверки RAG пока не проведены.
