# Как должна работать система

Этот документ объясняет технические правила будущего приложения простым языком. [Продуктовые требования](../product/product.md) имеют приоритет над предложенными здесь способами реализации. Код приложения, API-контракт и база данных пока не созданы. Выбор фреймворка, поставщика вакансий, модели и хранилища остаётся открытым.

## Что делает каждая часть

1. **Интерфейс** помогает выбрать направление, заполнить карту навыков, пройти короткую проверку, посмотреть рынок и вакансии, получить разбор и черновик письма.
2. **Сервер** хранит профиль и проверяет, что пользователь видит только свои данные. Он считает совпадение с вакансиями и зарплатную статистику по зафиксированным правилам.
3. **Загрузчик вакансий** получает записи из разрешённого источника, проверяет и сохраняет снимок данных на определённую дату. Демонстрационные записи имеют отдельную метку.
4. **База критериев** содержит подготовленные и проверенные описания навыков, требований уровней и вопросов. Только опубликованные разрешённые версии используются для новых результатов.
5. **Поиск и языковая модель** находят подходящие критерии и объясняют рассчитанный результат. Модель не определяет владельца профиля и не придумывает числа.

Один сервер с внутренними модулями возможен для первой версии, но это предложение, а не выбранный стек. Указанный в раннем каркасе FastAPI также не считается обязательным.

## Данные, которые нельзя потерять

В таблице слово «версия» означает номер или устойчивый идентификатор набора правил на момент результата. Старый опубликованный набор не переписывается: новая версия создаётся отдельно.

| Объект | Что сохраняем | Зачем |
|---|---|---|
| Роль и навык | Устойчивые ID, название, синонимы, связь с ролью, готовность каталога и проверок | Смена названия не должна менять смысл старого результата. |
| Критерий уровня | Роль, навык, конкретная тема, наблюдаемый признак, источник, версия и статус публикации | Можно объяснить, по какому правилу сделан вывод. |
| Профиль | Владелец, выбранная роль, условия поиска и номер изменения профиля | Чужой профиль нельзя открыть по ID; старый расчёт не выглядит актуальным после редактирования. |
| Доказательство | Навык, конкретная тема, тип («заявлено», «квиз», «кейс»), дата, версия и результат | Самооценка не смешивается с проверкой; краткий квиз не охватывает всю профессию. |
| Попытка и вопрос | Владелец, тема, закреплённая версия банка, состояние и ответы | Потеря связи и повторное завершение не создают неверный результат. Ключ ответа хранится только на сервере. |
| Вакансия и требование | Источник, внешний ID, оригинальный фрагмент, ссылка при наличии, даты, статус, режим demo/live, версия снимка | Можно проверить происхождение, убрать дубли и отличить старые данные от новых. |
| Совпадение и объяснение | Номер изменения профиля, снимок вакансии, версия расчёта, использованные критерии и источники | Результат воспроизводим; объяснение не отрывается от чисел. |

«Конкретная тема» в техническом контракте называется scope. Например, проверка SQL JOIN относится к JOIN, но не доказывает проектирование базы данных. «Происхождение» или provenance — это источник данных, версия и путь от исходного фрагмента до вывода. Эти термины нужны разработчику; человеку показывают «что проверено» и «откуда вывод».

Материал проходит состояния «черновик → на проверке → опубликован → выведен из новых расчётов». В новые ответы попадает только разрешённый опубликованный материал. Старые ответы продолжают ссылаться на свои версии. Загрузчик вакансий сначала проверяет записи во временной области, удаляет дубли и лишь потом делает новый снимок активным. Ошибка загрузки не выдаёт синтетические записи за свежие реальные.

## Режимы и состояния рынка

**Demo/live** отвечает на вопрос «данные демонстрационные или получены из внешнего источника?». **Active/stale/archived** отвечает на вопрос «актуальна ли вакансия?». Это разные признаки. Дата публикации работодателем и дата получения нами также различаются. У demo-вакансии может не быть настоящей ссылки; интерфейс в этом случае не создаёт её. Отсутствующая зарплата хранится как отсутствие значения, а не как ноль.

Если внешний источник недоступен, сайт показывает ошибку либо последний разрешённый снимок с отметкой «данные могли устареть». Он не подменяет реальные записи demo-данными без предупреждения.

## Расчёт совпадения с вакансией

Это **предложенная** версия правила matching-v0.1 для FR11. До реализации команда должна проверить веса и шкалу на примерах разных IT-ролей. Языковая модель не меняет формулу во время ответа.

Каждое требование вакансии связано с навыком и конкретной темой. У него есть важность w > 0, ожидаемый уровень r больше 0 и не выше 1, а также признак обязательности. Для совместимой темы s обозначает уровень, заявленный человеком, v — уровень, подтверждённый подходящей проверкой; оба числа от 0 до 1. Неизвестное доказательство даёт нулевой вклад в **подтверждённую долю**, но на экране остаётся «неизвестно», а не «не умеет».

Для одного требования: p = min(1, max(s, v) / r) и c = min(1, v / r). Для всех требований: P = 100 × сумма(w × p) / сумма(w); C = 100 × сумма(w × c) / сумма(w). P — покрытие по всему профилю, C — подтверждённая часть того же списка требований. Расчёт идёт без промежуточного округления; для показа число округляется один раз. Всегда 0 ≤ C ≤ P ≤ 100. Эти проценты не являются вероятностью найма.

**Проверочный пример:** четыре требования с весами 3, 3, 2, 2 и r = 1. Для Java s = 1 и v = 1; для API s = 0,75 и v = 0,5; для SQL s = 0,5 и v = 0; для CI оба значения 0. Получается P = 62,5%, на экране 63%; C = 45%. SQL заявлен, но не проверен; CI неизвестен. При нулевой сумме весов оба числа отсутствуют, причина — «недостаточно данных».

Обязательный навык с пробелом выводится отдельно. Язык, место, формат работы и необходимое разрешение имеют состояния «подходит», «не подходит», «неизвестно»; они не прячутся внутри процента. Проверка базовой темы не засчитывается за архитектурную тему. Для intern–senior и lead сравниваются опубликованные критерии конкретной роли; знания, практика и ответственность показываются отдельно. Общего порога, который официально присваивает человеку senior или lead, нет.

## Расчёт предложений зарплат

Это **предложенная** версия salary-v0.1 для FR09. Сначала выбираются уникальные реальные или уникальные demo-вакансии одной роли, региона, формата, валюты, периода оплаты, налогового режима и даты снимка. Эти группы не объединяются скрыто.

Основной показатель — медиана середины опубликованных **двусторонних** вилок: для каждой вакансии midpoint = (нижняя граница + верхняя граница) / 2. Квартили для отсортированных midpoint рассчитываются линейной интерполяцией на позициях (N − 1) × 0,25 и (N − 1) × 0,75. Предложения только «от» или только «до» показываются отдельно; пропущенная сумма, ноль и ошибка чтения исключаются с причиной. Показаны число всех вакансий, число с зарплатой и число пригодных для основной метрики.

Предлагаемый порог для агрегата — не менее 10 пригодных вилок. Ниже него показывается «недостаточно данных» и отдельные предложения. Порог требует продуктового решения. Нельзя смешивать gross с net, разные валюты или часовые и месячные суммы без проверенного пересчёта. Надпись результата: «медиана середины опубликованных вилок в выбранной выборке», а не «ваша будущая зарплата».

## Доступ, сбои и проверка

Сервер определяет владельца профиля по сессии и проверяет доступ к каждой попытке и результату. Браузер и текст вакансии считаются недоверенными. Ключи вопросов, секреты, чужие профили и тексты ответов не отправляются в модель или обычные логи. Защищённая cookie, CSRF, лимиты запросов, защита импорта и конкретные сроки хранения проектируются до live-запуска; их наличие пока не заявляется.

При отказе языковой модели числовой расчёт и исходные требования остаются доступны. При отсутствии критериев или сопоставимых вакансий показывается причина, а не выдуманный результат. Для реализации нужны проверки числового примера, пустой суммы весов, несовместимой темы, обязательного пробела, малой зарплатной выборки, повторного завершения попытки, смены версии профиля и чужого ID. Затем нужно проверить интерфейс на desktop и mobile. Сейчас это план проверок, а не проведённые тесты.
