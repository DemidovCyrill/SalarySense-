# Фронтенд SalarySense

Фронтенд запускается из корня репозитория командой `node app/frontend/demo/server.mjs`. Проверочный адрес — `http://127.0.0.1:4173`. Если порт занят, задайте `PORT` перед запуском. Демо проверено на Node.js 24.14.1. Для запуска дополнительных пакетов не требуется.

## Экраны и сценарии

## Редизайн

Первый экран раньше открывался общим обещанием, иллюстрацией и показателями профиля. На узком экране пример вакансии уходил ниже первого экрана, а на карте навыков фильтры сжимали поиск. В карточке вакансии оформление выделяло письмо сильнее, чем обязательные пробелы.

Для обзора сравнили две схемы.

```text
А  [Подробный разбор: оценки, навыки, источники] → [Что здесь можно сделать]
Б  [Задача и основное действие] | [Две оценки, две строки совпадения]
```

Выбрали вторую, потому что к цифрам сразу есть контекст. На мобильном порядок чтения идёт от задачи и действия к примеру, где одна строка покрыта, а другую стоит уточнить. Пример берёт данные из той же карточки вакансии, которая открывается по кнопке.

Навигация сгруппирована вокруг поиска работы, навыков и настроек сервиса. Повторяющиеся объекты показаны строками. Дополнительные фильтры и основания оценки раскрываются по запросу. Светлые поверхности, нейтральные подписи и зелёный акцент используются и на обзоре, и внутри приложения. Для разбора композиции, типографики и доступности вручную применили опубликованные рекомендации. [Impeccable](https://github.com/pbakaus/impeccable), [Vercel Web Interface Guidelines](https://github.com/vercel-labs/web-interface-guidelines)

В основном меню четыре входа — обзор, вакансии, навыки и рынок. Дополнительные пункты находятся в «Все разделы». Проверки и критерии доступны также из карты навыков. Второстепенные переходы оформлены как текстовые ссылки. Для частого действия используется основная кнопка с короткой подписью. Селекторы имеют общий вид и используют нативный `select`. Условия поиска и выборки раскрываются по запросу. [Atlassian Button](https://atlassian.design/components/button/usage), [Carbon Button](https://www.carbondesignsystem.com/building-blocks/core/components/button/guidelines), [GOV.UK Select](https://design-system.service.gov.uk/components/select/)

## Контракт подключения бэкенда

`app/frontend/public` содержит браузерные файлы, `public/api.js` — HTTP-клиент приложения, `app/frontend/demo` — отдельный локальный сервер и фикстуры. Клиент читает JSON через относительные адреса того же origin с cookie. Демосервер использует префикс `/api/v1` и отдельный маршрут `/ask` из учебного задания. Ошибки возвращаются с HTTP-статусом и полем `message`.

| Метод и путь в `/api/v1` | Данные |
| --- | --- |
| `GET /bootstrap` | Профиль с ревизией, каталог и готовность ролей, метаданные доступных проверок, режим источника, доступ в редакцию |
| `GET /profile`, `PATCH /profile`, `DELETE /profile` | Свой профиль. PATCH принимает отдельные условия или `claim: {id, rank}`, где `null` удаляет отметку. DELETE возвращает новую пустую сессию |
| `GET /market` | Параметры `roleId`, `region`, `format`, `mode`. Снимок, состояния источника, вакансии, распределение и причины исключений из зарплатной выборки |
| `GET /vacancies/:id` | Снимок вакансии, условия, исходные фрагменты, итог и вклад требований, ревизия профиля, версия расчёта, состояние объяснения |
| `POST /vacancies/:id/letter` | Принимает `{facts}` с ID выбранных заявлений и доказательств. Возвращает `{text}` |
| `GET /criteria/:roleId` | Опубликованные версии критериев по уровням |
| `POST /checks/:id/attempts`, `GET /attempts/:id` | Попытка привязана к версии банка и владельцу. Список вариантов, сохранённые ответы пользователя и результат при наличии |
| `PUT /attempts/:id/answers/:index`, `POST /attempts/:id/finish` | Сохранение варианта `{option}` и идемпотентное завершение |
| `GET /editor/materials` и изменения `/editor/materials/:id/:version` | Список, редактирование черновика, создание следующей версии через `/fork`, переход между состояниями через `/status` |

Типы заявленного опыта и границы зарплатного агрегата реализуют демонстрационные версии правил из [архитектуры](architecture.md). Смена роли меняет сравнение и проверки. Общие отметки опыта сохраняются по ID навыка. Проверка влияет на долю совпадения только при совпадении роли, навыка и темы. Вакансии и зарплаты подписаны как демоданные.

В карточке вакансии `explanation.state` принимает `ready`, `loading`, `insufficient-context` или `unavailable`. Для `ready` интерфейс ждёт `sections: [{text, citationIds}]` и `sources: [{id, title, fragment, version?, url?}]`. Раздел виден, если разрешаются все его ссылки на источники. Цифры совпадения и оригинальные фрагменты вакансии приходят отдельными полями и остаются доступны при сбое объяснения.

### Вопрос базе знаний

`POST /ask` принимает JSON `{"question":"Что подтверждает короткая проверка?"}`. Минимальная форма успешного ответа:

```json
{
  "answer": "Короткая проверка уточняет знание конкретной темы.",
  "sources": [
    {
      "id": "FR06",
      "title": "Результат проверки",
      "fragment": "Результат показывает проверенную тему, дату и версию."
    }
  ]
}
```

Источник может дополнительно содержать `page` и `url`. BM25 может отдавать собственные имена полей во внутреннем результате. На границе API их следует привести к форме выше. Ответ без сведений возвращает HTTP 200 с `sources: []`. Ошибка источника или модели возвращает статус ошибки, после чего пользователь может повторить вопрос. В локальном демо три группы заранее подготовленных вопросов покрывают оба сценария ответа.

## Границы демо

- Первый посетитель получает учебный профиль. Сессии и редакторские изменения живут в памяти процесса. Для рабочих данных понадобятся аутентификация, права редактора, защищённое хранилище, аудит публикаций и политика удаления.
- Проверки, критерии и вакансии покрывают демонстрационную глубину каждой роли. Ключи хранятся в серверной части. Редактор может ввести новый ключ при изменении вариантов и получает из банка только формулировки и варианты. Соискатель видит обратную связь по своей попытке.
- Подключение реальных вакансий, BM25, утверждённый корпус, вызов модели и бенчмарк остаются этапом бэкенда. Черновик письма собирает локальный сервер из выбранных фактов.

## Проверки

Команда для воспроизведения проверок демо-API:

```powershell
node --test tests/frontend-smoke.test.mjs
```

- Демо-API: расчёт 63% и 45% из архитектурного примера, несовместимая тема, малый рынок, изоляция двух сессий, повторное завершение, публикация версии банка, сохранение исходной версии попытки, удаление профиля и ответы `/ask`.
- Edge и Playwright: основной сценарий на 1440 × 900, переходы и ширина на 390 × 844, клавиатурный переход к содержанию, фокус диалога, фильтры рынка и вакансий, разрыв запроса, копирование письма и восстановление квиза после перезагрузки.
- Axe-core 4.12.1: проверка 14 маршрутов на обеих ширинах и диалога удаления. После исправления контраста при анимации сканер не обнаружил нарушений по выбранным правилам WCAG A/AA. Полная ручная проверка со скринридерами остаётся открытой.

### Повторная проверка после редизайна

- В Edge с Playwright на 1440 px пройден путь от клавиатурного открытия примера до обеих оценок, раскрытия требования, подготовки и копирования письма. Отдельно пройдены поиск вакансий без результатов и сброс, смена роли, запись опыта в карту, восстановление квиза, сравнение зарплат, отказ источника, загрузка и повтор вопроса к базе, публикация версии критерия и удаление профиля.

- `node --check`, `node --test tests/frontend-smoke.test.mjs` и `git diff --check` прошли. В проекте браузерные файлы обслуживаются напрямую. Отдельные команды сборки, линтера и проверки типов отсутствуют.
